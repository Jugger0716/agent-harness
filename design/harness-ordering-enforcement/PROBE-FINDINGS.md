세 결과가 P-9·P-10에 동시에 답한다. **단계 P 재기동에 얹으면 재기동 비용이 1회로 끝난다.**

**실행 시 정정 2건:**
1. **재기동은 필요 없었다** — §1-14 정정 참조. 프로브 스킬은 다음 사용자 메시지 직후 로드됐다.
2. **관측 ②(서브에이전트 전파)는 실측하지 못했다.** 프로브 턴 동안 `Agent`/`Task` 도구가
   **함께 사라졌기 때문**이다(`ToolSearch select:Agent,Task` → 미발견; 다음 턴에는 정상 반환).

   서브에이전트로 우회하는 경로가 도구 자체의 제거로 닫힌다.

   `disallowed-tools: Bash` 스킬 안에서 `Agent`를 **직접 호출**해 보아야 한다 — 미실행.

## §3. 조사 과정에서 폐기된 설계안 — 폐기 사유를 남긴다

같은 안을 다음 세션이 다시 제안하지 않도록, **왜 죽었는지**를 근거와 함께 기록한다.

| 안 | 폐기 사유 |
|---|---|
| **A — phase 그래프 집행** (훅이 `state.json`의 `phase`를 읽어 판정) | `phase`는 **모델이 쓴다**. 단계를 건너뛴 모델은 phase도 같이 위조할 수 있다 |
| **B — 아티팩트·영수증 집행** (게이트가 영수증 파일을 남기고 다음 노드가 그것을 요구) | **영수증도 모델이 쓴다.** 위조 비용이 「필드 한 줄」에서 「셸 명령 한 줄」로 올라갔을 뿐. 「훅이 엔진 관측 사실을 기록하면 위조 불가」 가설은 §1-8(훅 미발화)에서 죽고, 성립했더라도 §1-9(격리 0)에서 다시 죽는다 |
| **B′ — 훅 + 트랜스크립트 검증** | 훅이 게이트를 못 보므로(§1-8) 가로채는 순간에 판정하려면 결국 트랜스크립트를 읽어야 하고, 그러면 훅은 타이밍만 제공하는 껍데기다. 대가는 전 세션 전 도구 가로채기 + 개별 훅 kill switch 부재 + **CRLF 한 번이면 `exit 2`(= deny 코드)로 전면 차단** |
| **트랜스크립트 사후 정합성 검증 (초안)** | 「산출물 쓰기가 게이트보다 먼저였는가」 술어가 **쓰기 가능 호출의 72%를 못 본다**(§4 실측). 세션 파일 식별용 논스에 필요한 `run_counter`는 저장소에 0건이고, `.harness/`가 종료 경로 9곳에서 삭제되어 **런 사이 지속이 원리적으로 불가** |

**살아남은 축소판**: 게이트 시퀀스만 검증. `AskUserQuestion`은 트랜스크립트에서 **완전히 관측된다**
(이 프로젝트 39개 트랜스크립트에서 245건). 못 보는 것은 *산출물 쓰기*이지 *게이트*가 아니다.

## §5. 현재 유력한 방향 (설계 확정 아님)

**능력 기반 순서** — 단계별로 스킬을 쪼개고, 각 단계에서 **그 단계가 하면 안 되는 일에 필요한
도구를 제거**한다. 순서를 *선언*으로 강제하는 대신, 순서를 어겨도 **어길 수 있는 일이 없게** 만든다.

§1-1~7이 이 방향의 전제를 대부분 실증했다: 경로 스코프가 동작하고, 셸 쓰기를 잡고, 서브에이전트까지
전파된다. ~~**남은 전제는 P-9·P-10 둘뿐이다.**~~ → **2026-09-01 해소(§2). 그리고 그 답이 이 방향의
설계를 한 군데 바꾼다:**

- **스킬 단위 도구 제거는 동작한다** (P-9 ⓐ) — 「능력 기반 순서」의 핵심 전제는 살아 있다.
- **그러나 스킬 frontmatter에서는 경로 스코프를 쓸 수 없다** (P-9 ⓑ, no-op). §1-1~7이 실증한
  경로 스코프 차단은 **`settings.json`의 `permissions.deny` 표면 전용**이다. 따라서 단계별로
  「이 경로에만 못 쓰게」는 스킬 분할만으로 달성 불가이며, 남는 수단은 **도구 자체를 통째로 빼는 것**뿐이다
  (예: 게이트 전 단계에서 `Bash`·`Write`·`Edit`를 통째로 제거). 이는 §5가 이미 인정한
  「인터프리터 쓰기 구멍은 `Bash` 자체를 제거해야만 닫힌다」와 같은 결론에 다른 경로로 도달한 것이다.
- **턴 범위라는 사실이 오히려 유리하다** (P-10) — 계획 스킬이 같은 턴에 build 스킬을 불러
  스스로 무장해제하는 경로가 **구조적으로 막힌다**. 단계 전환에 사용자 메시지 1회가 강제되며,
  그것이 곧 게이트다.

정직하게 남는 한계:
- **인터프리터 쓰기 구멍**(§1-6)은 `Bash` 자체를 제거해야만 닫힌다.
- **`/harness-build`를 처음부터 부르는 것은 못 막는다** — 순서 선언 필드가 없다(§1-16).
  다만 이는 드리프트가 아니라 명시적 선택이라 위협 모델이 다르다.
- 따라서 광고 가능한 명제는 **「게이트 전 구현 불가」가 아니라 「게이트 전 기존 파일 수정·명령 실행 불가」**다.

병행 조사(별도 워크플로)가 분할 경계와 예산을 냈다: 최소 분할은 **Step 3.5 뒤 / Step 4 앞** 한 곳,
description 예산은 harness 500 + harness-build 424 → 총 **7,295 / 8,000**(여유 705자).
단 적대 3렌즈가 BLOCKING 3건(게이트의 mtime 의존, `Modify` 옵션의 기존 파일 수정, epic 경로 좌초)을
내어 **분할안 자체는 재설계가 필요하다**.

> `plan_critic.counts` (lowercase keys) and `verify.cold_counts` (uppercase keys) follow different upstream schemas (`CriticReport.counts` lowercase keys vs. `CriticReport.items[].severity` uppercase values; the lowercase `FindingSchema.severity` in that same file is a THIRD, unrelated vocabulary) — an intentional difference, NOT normalized to one case.
> `spec_stamp.generation` and `plan_critic.round` are DIFFERENT axes and the word "revision" in this file belongs to the latter: `round` marks the Auto-revise **revision opportunity** as spent (bounded at 1 — every converge run-end mapping writes `1`), while `generation` counts spec.md **writes** (unbounded). `converge.rounds` is a third, unrelated counter — loop rounds, display only — and none of the three is compared with another. A session can advance `generation` many times with `round` still `0` — a Modify loop does exactly that. They are never compared to each other.
> `plan_critic.applied`'s value set (`executed`/`skipped`/`failed`) is harness-local and is NOT interchangeable with /spec `state.critic.applied`'s value set (`approved`/`pending`/`revised`) — the field name is borrowed from /spec `state.critic`, the value set is not.
> `cli_flags.epic` is tri-state (`null`/`true`/`false`) while `cli_flags.cold_pass` is a plain boolean — `--epic`+`--no-epic` given together can halt on that distinction (two explicit, opposite non-null values) rather than collapsing onto one boolean.
> A per-session cold-pass execution cap equal to `max_rounds` (default 3) is not a separate counter — it falls out arithmetically from `verify.cold_round`'s once-per-round execution latch.
> `cli_flags.output_dir` remains audit/record only (see the `docs_path usage rule` note at Step 1 item 10.5) — no section recomputes from it, only `docs_path` itself is read directly (`skills/harness/SKILL.md` §Session Recovery's docs_path drift check does not read this field either). `cli_flags.epic` and `cli_flags.cold_pass` are NOT audit-only: `cli_flags.epic` is written by `skills/harness/SKILL.md` §Step 1 CLI Parsing and read by `skills/harness/SKILL.md` §Scale Assessment's override check, `skills/harness-gate/SKILL.md` §Step 3 Pass B and `skills/harness/SKILL.md` §Approval Gate (Pass B's leading-option table, applied); `cli_flags.cold_pass` is written by `skills/harness/SKILL.md` §Step 1 CLI Parsing and read by the `cold_dispatch_allowed` predicate (`skills/harness-build/SKILL.md` §Step 5 "Cold Review Input Collection", this slice).
> `cli_flags.cold_pass_source` is likewise NOT audit-only: it is written once at Setup (same write as `cli_flags.cold_pass`) and read by every site that renders the disabled reason — it is never re-derived.
> `plan_critic.*`, `scale.*`, `cli_flags.epic`/`cli_flags.cold_pass`, `epic.*`, and now `verify.cold_*` are all written by the sections named in the table above (this slice).
